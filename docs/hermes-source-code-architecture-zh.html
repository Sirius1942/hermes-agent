Source Code & Architecture Guide

Hermes Agent 源代码与项目架构解读

基于当前仓库真实代码整理，重点解释 Agent 窄腰、Prompt 缓存、Provider/Transport、 Tool Registry、多端接入、SessionDB、Skills、Memory、Plugin、Subagent 与 Cron 的职责边界。

中文 更新：2026-07-21 离线 HTML 源码导读

1. 核心结论

Hermes Agent 是一个以同步 AIAgent 为窄腰、以插件和协议适配器向外扩展的模块化单体。 CLI、消息平台、TUI、Web Dashboard、Electron Desktop、ACP 和 Cron 看起来像多个产品， 但最终都复用同一套 Agent、工具、Provider、会话和学习基础设施。

Narrow Waist

统一 Agent 核心

所有接入面最终调用 AIAgent.run_conversation()，平台差异留在输入、授权、排队和输出投影层。

Cache First

Prompt 缓存优先

系统提示词在会话内冻结并持久化；动态记忆、Skill、Steer 等通过消息或请求副本注入。

Edges Expand

能力向边缘扩展

优先使用现有代码、CLI + Skill、服务门控工具、Plugin 或 MCP，Core Tool 是最后选择。

架构定位： 这不是微服务系统。它是一个 Python Agent 核心，加上 Node/React/Electron 外壳， 通过本地进程、PTY 和 JSON-RPC 组织起来的多端个人 Agent 运行时。

最重要的职责边界如下：

  • 接入层：用户从哪里来、如何授权、如何展示、如何排队和打断。
  • Agent 核心：模型调用、工具循环、重试、Fallback、压缩和回合收尾。
  • Provider Transport：不同模型 API 的请求和响应格式。
  • Tool Runtime：模型能看到哪些工具、工具调用能否执行、结果如何回写。
  • SessionDB：跨进程、跨界面、跨重启的持久会话。
  • Learning Layer：长期记忆、程序性知识和上下文管理，但不得破坏提示缓存。

3. 启动入口与运行形态

安装后的命令入口由 pyproject.toml 声明： 

[project.scripts]
hermes = "hermes_cli.main:main"

聊天启动链可以简化为：

hermes
  → hermes_cli.main.main()
  → cmd_chat()
      ├─ classic CLI → cli.main() → HermesCLI
      └─ TUI         → Node Ink TUI → tui_gateway.entry

hermes_cli/main.py

产品级进程路由器。处理 Profile、Windows/Termux 启动、Setup、Gateway、Dashboard、Desktop、Cron、ACP、升级和恢复。

cli.py

经典聊天界面。处理 prompt_toolkit、Rich、皮肤、Slash 命令、图片附加、Agent 构造和交互式审批。

阅读提示： hermes_cli/main.py 负责“启动哪个产品面”，cli.py 负责“经典终端怎么交互”， run_agent.py 与 agent/ 才负责“Agent 怎么执行”。

5. System Prompt 与提示缓存

系统提示词由 agent/system_prompt.py 按三层构造，并缓存到 agent._cached_system_prompt：

Stable

稳定层

SOUL/默认身份、工具规范、Skills 索引、平台提示、环境信息、模型家族规则。

Context

上下文层

调用者 System Message、AGENTS.md、CLAUDE.md、.cursorrules 等项目文件。

Session Frozen

会话冻结层

MEMORY/USER 快照、Provider 静态说明、时间、Session、Model 和 Provider 身份。

构造后的完整字符串会写入 SessionDB.sessions.system_prompt。Gateway 后续重新创建 AIAgent 时优先从数据库恢复完全相同的字符串，而不是重新扫描磁盘。

关键策略： 外部记忆召回、Plugin 动态上下文、MoA 上下文、Prefill、Anthropic Cache Control、Gateway 恢复说明等， 只写入本轮 API 请求副本或当前消息，不改持久化 System Prompt。

为什么消息副本与持久历史分离

  • 避免内部提示进入长期 Transcript。
  • 避免恢复 Session 时把 Memory Context 误当成用户原话。
  • 保持严格的 User / Assistant / Tool 角色关系。
  • 允许不同 Provider 在发送前做协议级修复，不污染规范消息。
哪些操作会正常打破缓存？
显式切换 Model/Provider、进入新的 Session、某些压缩或运行时模式切换会导致 Prompt 身份或缓存键变化。 普通用户回合、Skill 调用、Goal Continuation 和动态 Memory Prefetch 不应该重建 System Prompt。

6. Provider、Runtime 与 Transport

模型接入被拆为三个不同问题：

ProviderProfile

声明服务特性：名称、别名、认证、Base URL、API Mode、Vision、Header、Token 限制和请求特殊参数。

Runtime Provider

解析本次调用的实际 Model、凭据、Base URL、API Mode、OAuth/Key、Credential Pool 和 Fallback。

Transport

负责网络线协议：消息转换、工具 Schema、请求参数、响应校验和统一标准化。

Provider Profile = 这个服务具有什么能力和约束
Runtime Provider = 这次具体用哪个模型、地址与凭据
Transport        = 请求和响应在网络线上长什么样

Provider 插件位于：

plugins/model-providers/<provider>/
├── __init__.py
└── plugin.yaml

主要 API 模式包括：

  • chat_completions：OpenAI 兼容接口。
  • codex_responses：OpenAI Responses/Codex 风格接口。
  • anthropic_messages：Anthropic Messages。
  • bedrock_converse：AWS Bedrock Converse。
  • codex_app_server：可选的整回合旁路运行时。

所有 Transport 最终归一化到相同内部响应，使 Conversation Loop 不必分别理解每个 Provider 的 Tool Call 和 Reasoning 格式。

7. Tool Registry、Toolset 与执行安全

每个内置工具文件在模块顶层调用 registry.register()。发现器通过 AST 判断 tools/*.py 是否包含顶层注册调用，再导入真正的工具模块。 

tools/registry.py
      ↑
tools/*.py              # 模块导入时自注册
      ↑
model_tools.py          # Schema 组装与统一分发
      ↑
run_agent / CLI / Gateway / Cron / ACP

一个工具条目包含什么

  • 工具名称和 JSON Schema。
  • Handler。
  • 所属 Toolset。
  • check_fn 服务可用性检查。
  • 是否异步、环境变量要求、显示 Emoji。
  • 最大结果大小和动态 Schema Override。

Toolset 的作用

Toolset 把工具组合成 web、terminal、file、 browser、coding、hermes-cli、 hermes-cron、hermes-acp 等平台或场景集合。

Webhook 特例： 公共 Webhook 可能携带 PR 标题、评论等不可信内容，因此默认只暴露受限 Web/Vision/Clarify 能力， 不授予终端和文件写入。

工具调用流水线

模型参数
  → 按 Schema 修正类型
  → Tool Search Bridge 解包与 Scope 检查
  → Tool Request Middleware
  → Plugin pre_tool_call
  → Block / Approve
  → ACP 编辑审批
  → Checkpoint
  → Registry.dispatch()
  → Tool Execution Middleware
  → post_tool_call
  → transform_tool_result
  → 结果写回消息历史

并发执行

  • 最多 8 个工具 Worker。
  • 只读工具或路径互不冲突的文件操作可并发。
  • 结果仍按模型原始 Tool Call 顺序写回。
  • 传播 ContextVar、Profile 和审批回调。
  • 支持 Worker 级精确中断、Heartbeat 和超时。
  • 按模型 Context Window 缩放工具输出预算，过大结果可落盘。
为什么 Core Tool 门槛高： 工具 Schema 会随每次模型请求发送。Core Tool 越多，所有用户每回合承担的 Token、延迟和模型选择负担越大。

9. SessionDB 与状态模型

hermes_state.py 中的 SessionDB 是规范会话存储，JSON Snapshot 只是可选兼容输出。

存储能力

  • SQLite + WAL。
  • NFS/SMB/FUSE 下回退 DELETE Journal。
  • Session 与 Message 表。
  • FTS5 与 CJK Trigram 搜索。
  • 标题、来源、Model Config。

会话生命周期

  • Branch 与 Compression Lineage。
  • Delegate Child。
  • Rewind / Undo。
  • Gateway Routing。
  • Compression Lock 与 Cooldown。
Gateway 路由身份：session_key
持久对话身份：session_id

同一个 session_key 可以切换到不同 session_id；
压缩可以旋转 session_id，但保持平台路由不变。

Tool Executor 还会在重要工具步骤后增量刷新 SessionDB，避免 Agent 执行重启或破坏性工具后， 已完成的 Tool Call/Result 因进程退出而丢失。

10. Skills、Memory 与 Context Engine

内置 Memory：冻结快照

$HERMES_HOME/memories/MEMORY.md
$HERMES_HOME/memories/USER.md
  1. Agent 创建时读取文件并进行威胁扫描。
  2. 生成 System Prompt 快照。
  3. 会话中 memory 工具可以立即写磁盘。
  4. 当前会话的 Prompt 快照不变。
  5. 新会话才加载更新后的内容。

外部 Memory Provider

MemoryProvider 提供初始化、静态 Prompt Block、动态 Prefetch、回合同步、工具 Schema、 压缩前提取、Session 切换和 Session 结束 Hook。系统只允许一个外部 Provider，避免 Schema 膨胀和多后端写入冲突。

动态 prefetch() 结果作为本回合临时 Memory Context 注入，不修改已缓存 System Prompt。 回合结束同步在单 Worker 后台线程串行执行，不阻塞用户收到回答。

Skills：渐进式披露

System Prompt：Skill 名称和描述索引
        ↓
skill_view(name)
        ↓
完整 SKILL.md
        ↓
按需读取 references / scripts / templates / assets

/skill-name 调用会把完整 Skill 内容包装成当前 User 消息，而不是修改 System Prompt。 MemoryManager 能识别 Skill 脚手架，只把真实用户指令写入外部记忆。

Context Engine

默认 ContextCompressor 负责：

  • 根据 Context Window 计算压缩阈值。
  • 保护开头目标与当前任务尾部。
  • 对中间区域生成摘要。
  • 保持 Tool Call/Result 配对。
  • 支持 Focus Compression、Session Split 和 In-Place Compaction。
  • 压缩失败时记录 Session 级 Cooldown，避免每回合重复失败。

12. Subagent 与 Cron

Subagent

  • 全新历史和独立 Task/Session ID。
  • 继承 Provider、Model、Reasoning 和 Fallback。
  • 默认跳过 Memory。
  • 工具集被收窄，Leaf 不可递归委派。
  • 父 Agent 只看到最终摘要。
  • 支持后台 Fan-out、并发上限和最大深度。

Cron

  • 每次触发创建全新受限 Agent。
  • 禁用 cronjob、messaging、clarify。
  • 跳过用户 Memory，防止自动任务污染画像。
  • 支持 Skill、Workdir、MCP 和多平台投递。
  • Provider/Model Drift 失败关闭，防止意外消费。
  • 使用无活动时间检测挂起，而非简单总时长。

两者都没有实现另一套 Agent：只是用不同的 Session、Prompt、Toolset 和安全策略重新实例化主 AIAgent。

13. 配置、Secret 与 Profile 隔离

get_hermes_home() 是用户状态路径的单一事实来源。

~/.hermes/
├── config.yaml       # 行为与配置
├── .env              # API Key / Token / 密码
├── state.db          # 会话规范存储
├── memories/
├── skills/
├── plugins/
├── cron/
├── logs/
└── profiles/
    └── coder/
        ├── config.yaml
        ├── .env
        ├── state.db
        ├── memories/
        ├── skills/
        └── plugins/

Profile 本质上是独立的 HERMES_HOME，因此配置、凭据、SOUL、Memory、Skills、Plugins、SessionDB、Cron 和 Gateway 都隔离。

配置原则： 用户行为、阈值、显示和启用状态进入 config.yaml；Secret 进入 .env。 某些历史代码仍用内部环境变量做进程桥接，但不应继续用新环境变量扩大用户行为配置面。

15. 架构优点、成本与风险

主要优点

  • Prompt 缓存约束落实到数据库恢复、Skill 和 Memory 机制。
  • 所有界面共享同一 Agent 核心，行为不易分叉。
  • Provider 差异由 Profile、Runtime、Transport 分层吸收。
  • 工具前后有 Scope、审批、Checkpoint、Middleware 和 Hook。
  • 长驻进程、中断、重启和跨平台失败恢复非常成熟。

主要成本

  • Gateway、Classic CLI 和 TUI Gateway 仍是超大编排文件。
  • Plugin、Provider、MCP、Skill 等扩展面较多，学习曲线高。
  • 同步 Agent 与异步外壳之间需要复杂 Executor 和 ContextVar 桥。
  • Import-Time Registry、Thread Local 和环境变量带来隐藏耦合。
  • 兼容旧测试和第三方调用导致薄转发与间接访问较多。
