# 二次开发设计讨论

**状态：** 已收口并转入 `iteration-02`  
**所属迭代：** `iteration-01`  
**规划与设计循环：** `DGL-001`（已完成），当前为 `DGL-002`  
**目标：** 在不破坏 Hermes Agent 核心不变量的前提下，确定第一条可交付的二次开发路线

## 1. 当前问题

项目已经具备 Agent Loop、多个交付表面、插件/Skill/MCP 扩展和完整官网开发指南，但这些信息分散在源码和英文文档中。二次开发如果直接从 `run_agent.py` 或某个 UI 入口开始，容易出现以下问题：

- 把应属于 Skill、Plugin 或 MCP 的能力错误地加入核心工具 Schema；
- 只修复 CLI，遗漏 Gateway、Cron、ACP、API 或辅助模型调用者；
- 在会话中途修改系统提示词或工具集，破坏 Prompt caching；
- 将非秘密行为设置写进 `.env`，或把 Profile 数据写到共享路径；
- 在 Dashboard 中重复实现 TUI 聊天，形成两套不一致的主流程；
- 用 mock 或静态页面证明功能完成，却没有真实配置、持久化、网络失败和恢复证据。

本轮先建立面向二次开发的中文架构基线，不预设具体业务产品，也不提交猜测性的核心代码。

## 2. 已确认的架构事实

| 事实 | 对二开的影响 |
| --- | --- |
| `AIAgent` 是共享执行中心 | 共享行为改动必须检查所有入口和缓存/消息历史 |
| 内部消息统一为 OpenAI 风格 | Provider adapter 负责格式转换，业务逻辑不应绑定某一家 API |
| 工具由注册表发现，toolset 控制暴露 | 新工具会增加每次调用的 Schema 成本，优先降低 footprint |
| Provider、Platform、Memory、Context Engine 有插件路径 | 第三方或部署专属能力应留在插件目录或独立插件仓库 |
| Skill 可通过现有工具完成工作流 | 业务流程、CLI 编排和知识型能力的默认入口是 Skill |
| Dashboard 嵌入真实 `hermes --tui` | 不在 Dashboard 重写 transcript/composer |
| Desktop 是独立聊天表面 | Desktop 功能可以单独设计，但共享协议必须保持兼容 |
| 行为配置使用 `config.yaml`，秘密使用 `.env` | 新设置需声明配置归属和迁移/默认值 |
| 所有 Profile 路径通过 `get_hermes_home()` | 不能硬编码 `~/.hermes`，否则会跨 Profile 泄露状态 |

详细说明见 `.pb/design/SECONDARY_DEVELOPMENT_ARCHITECTURE.md`。

## 3. 本轮设计问题

我们要决定的不是“下一步改哪个文件”，而是：

1. 第一条二开垂直切片服务哪个真实用户场景？
2. 它的主交付表面是什么：CLI、Gateway、TUI、Desktop、ACP、API 还是 Python？
3. 能否用 Skill、Plugin、MCP 或已有服务门控完成，而不增加核心 Schema？
4. 哪些配置、秘密、Profile 数据和外部网络边界需要明确？
5. 以什么真实产物证明完成：命令输出、消息收发、UI 操作、持久化记录、协议调用还是端到端任务？

## 4. 候选方向

| 方向 | 默认扩展方式 | 适合场景 | 主要风险 | 当前判断 |
| --- | --- | --- | --- | --- |
| 团队工作流/知识助手 | Skill + CLI（必要时 Plugin） | 研究、代码、文档、运维流程 | 指令不完整、依赖外部 CLI | 最适合第一条低 footprint 切片 |
| 新模型或推理服务 | Model Provider Plugin | OpenAI 兼容服务、模型目录、凭据接入 | API mode、回退、辅助模型和认证链不一致 | 有真实 Provider 时再做 |
| 新结构化外部能力 | Plugin 或 MCP | 专用 API、二进制、流式、精确 Schema | 凭据、网络、远程数据泄露 | 先验证 Skill 是否足够 |
| 新消息平台 | Platform Plugin/Adapter | 新 IM、企业平台、Webhook | 授权、并发、分片和交付失败 | 需要明确平台和运营责任 |
| 长期记忆或上下文策略 | Memory/Context Engine Plugin | 跨会话知识、压缩和检索 | 隐私、Profile 隔离、缓存和丢失信息 | 属于高风险设计切片 |
| 新聊天体验 | TUI Gateway 或 Desktop | 自定义交互、桌面工作台 | 协议漂移、状态重复、视觉回归 | 先选定产品表面，不并行重做 |

## 5. 推荐起步方案

在用户尚未指定业务域之前，建议把第一条正式产品迭代限定为“一个真实工作流的低 footprint 垂直切片”：

1. 以 Skill 为默认起点，确认现有 `terminal`、`file`、`web` 或其他工具能够覆盖最小流程。
2. 只有出现结构化认证、可靠状态或精确处理需求时，才增加 Plugin/MCP；把核心工具列为最后选项。
3. 只选择一个主表面，其他表面先记录为非目标；避免在没有用户场景时同时改 CLI、Gateway、TUI 和 Desktop。
4. 用临时 `HERMES_HOME` 验证配置、Profile、持久化和秘密边界；对外部服务使用明确的失败和超时策略。
5. 完成一个端到端流程后，再评估是否需要共享核心抽象或扩展第二个表面。

这不是对业务方向的最终决定，而是规划与设计循环的默认假设；用户提供真实场景后，可以在 `DGL-002` 或 `DGL-004` 阶段调整。

## 6. TestLoop 设计验收标准

后续方案至少要回答：

- 是否忠实解决一个可复现的用户问题；
- 是否保护 Prompt caching、消息角色交替、Profile 隔离和配置权威；
- 是否选择了足够低的 Footprint；
- 是否包含正向、负向、中断、恢复和清理契约；
- 是否能由 TestLoop 验收者在全新上下文中访问真实产物；
- 是否有清晰的回滚、升级和上游同步边界。

按 `.loops/RUBRICS.md` 验收时，关键维度必须达到 `4/5`，总体至少 `4/5`，阻塞项必须为零。TestLoop 验收者不得修改被验收的设计或产品代码。

## 7. 待用户确认的决策项

以下信息会决定下一轮设计的范围；在得到答案前，规划与设计循环可以继续整理约束，但不应凭空实现业务功能：

| 决策项 | 需要明确的内容 |
| --- | --- |
| 业务场景 | 要解决的具体任务、目标用户和成功结果 |
| 主表面 | CLI、Gateway、TUI、Desktop、ACP、API 或 Python |
| 外部依赖 | Provider、第三方 API、企业平台、本地服务或无外部依赖 |
| 部署边界 | 本地单用户、团队共享、远程沙箱、容器或多 Profile |
| 合规与隐私 | 哪些工作区内容可以离开本机，日志和记忆保留多久 |
| 验收产物 | 需要看到的命令、消息、UI、协议响应、数据库记录或报告 |

```text
DGL-001  判断完整 DesignLoop 的必要性、预算和人类门禁（已完成）
  → DGL-002  固化业务问题、证据、范围和非目标
  → DGL-003  核对仓库意图、官网约束和真实运行产物
  → DGL-004  比较 Skill / Plugin / MCP / 核心方案及其权衡
  → DGL-005  形成设计契约、量表和单迭代验收条件
  → DGL-006  产出方案和可测试原型
  → DGL-007  向 TestLoop 提交设计验收
  → TestLoop  使用全新上下文返回 pass / fix / pivot / stop
  → DGL-008  由规划与设计者根据验收结论修订或请求人类决策
  → DGL-009  仅将 TestLoop 已验收的设计交接给 DevLoop 开发者
```
