# 迭代 03 设计讨论：聊天优先的 macOS 工作台

## 1. 诊断

上一轮选择 SwiftUI + 受控 `WKWebView` 是正确的首版边界：完整 Dashboard、Chat PTY、动态
插件和认证都已经真实可用。当前需要优化的是“入口和层级”，不是复制更多后端能力。

因此本轮把 App 视为两层：

```text
聊天工作台（默认）
  └─ 真实 Dashboard /chat：transcript、composer、流式输出、工具活动、会话

管理中心（次级）
  └─ 真实 Dashboard 其他页面：Models、Files、Plugins、MCP、Channels、Cron、System、Docs…
```

SwiftUI 只拥有窗口、连接状态、导航层级、错误恢复和低频设置；聊天数据和交互仍归 Dashboard
所有。这样可以改善入口体验而不制造第二个消息事实源。

## 2. 方案比较

### 方案 A：轻量聊天优先壳（推荐）

- 默认 URL 解析为当前 Dashboard 的 `/chat` 入口。
- 顶部只保留连接状态、会话/聊天入口、管理中心和必要的重新连接动作。
- 保留现有 WebView Chat，不在 Swift 中绘制第二套 transcript 或 composer。
- 明快主题、浏览器外开、手动 Hermes 路径、自动启动等动作进入高级设置或上下文菜单。

**优点：** 改动集中在 App 壳层；不增加核心工具和协议；最大程度复用现有 Chat PTY；回滚
简单；可以快速通过真实 App 验收。

**风险：** `/chat` 深链接和 WebView 内部导航需要验证；如果通过 CSS 隐藏 Dashboard 元素，
   可能随 WebUI 版本变化，因此应优先使用路由和壳层层级，不依赖脆弱 DOM 选择器。

### 方案 B：原生 Swift 聊天客户端

- Swift 直接接入 `tui_gateway` 或现有服务端 JSON-RPC。
- Swift 自己渲染消息、工具活动、停止、重试、附件和会话列表。

**优点：** 可以针对 macOS 做最完整的焦点、快捷键、菜单和多窗口体验。

**拒绝原因：** 会复制 `apps/desktop` 的聊天表面和状态机；需要处理 JSON-RPC、流式事件、
   认证、附件、工具批准、会话恢复和协议版本；短期内不能证明比真实 TUI/Dashboard 更完整。
   这是独立产品方向，不适合本轮“优化并收敛”。

### 方案 C：保持当前完整 Dashboard 根入口

- 只微调颜色、工具栏文案和连接提示，不改变入口层级。

**优点：** footprint 最小、几乎无兼容风险。

**拒绝原因：** 无法解决聊天用户打开后先面对管理型导航的问题；低频基础设施仍与聊天动作
   混在一起，用户体验收益不足。

## 3. 功能收敛建议

| 能力 | 处理建议 | 原因 |
| --- | --- | --- |
| `/chat`、transcript、composer、流式输出、工具活动 | 保留并设为默认 | 是 App 的核心结果，已有真实实现 |
| 会话继续、重试、连接状态 | 保留并提高层级 | 直接影响聊天连续性和可恢复性 |
| 完整 Dashboard 管理页面 | 保留，移到“管理中心” | 不能删除已有 WebUI 能力，但不应干扰聊天 |
| 明快主题切换 | 从主工具栏移到高级外观设置 | 低频且不属于聊天动作；默认主题可保留 |
| 在浏览器中打开 | 从主工具栏移到菜单 / 管理中心 | 逃生舱功能，不是聊天高频动作 |
| 重新加载 | 保留在连接失败状态和菜单 | 正常聊天状态不需要一直占一个按钮 |
| Hermes 可执行文件路径 | 高级连接设置 | 仅本机自动启动或诊断时需要 |
| 自动启动本地 Dashboard | 暂保留，改为高级开关或首次失败时动作 | 便利性有价值，但启动等待不应遮蔽聊天状态 |
| 原生 Swift transcript / composer | 本轮不做 | 避免第二事实源和与 TUI/Desktop 漂移 |

## 4. 推荐交互流

### 4.1 正常进入

```text
打开 App
  → 检查 Dashboard
  → 可达：进入 /chat
  → 不可达：显示“正在启动 / 连接”与明确进度
  → 连接成功：进入 /chat，并保留会话上下文
```

### 4.2 失败恢复

```text
连接失败
  → 主按钮：重试连接
  → 次按钮：连接设置
  → 辅助入口：管理中心 / 在浏览器打开
  → 不显示空白 WebView，不自动丢弃已有配置
```

### 4.3 聊天与管理切换

- 默认窗口标题和焦点落在当前聊天页面。
- “管理中心”进入同一 Dashboard 的管理路由，必要时提供返回聊天按钮。
- 不在 Swift 壳中复制页面级导航数据；路由是否可直接深链由 TestLoop 用真实 Dashboard 验证。

## 5. 交互候选

以下快捷键进入设计契约前仍是候选，不应直接编码：

| 操作 | 候选快捷键 | 预期结果 |
| --- | --- | --- |
| 新建聊天 | `⌘N` | 调用现有 Dashboard 新会话入口，不创建 Swift 私有会话 |
| 聚焦输入 | `⌘L` | 将焦点交给真实 WebView composer；若 WebUI 不支持则不实现 |
| 重试连接 | `⌘R` | 仅在连接失败或用户明确触发时重载，不打断正常流式输出 |
| 打开管理中心 | `⌘⇧,` | 进入完整 Dashboard 管理入口 |

这些快捷键必须先确认是否与 macOS、WebView 和 Dashboard 已有行为冲突；不能为了“看起来像
原生”而引入无法验证的 JS 注入。

## 6. 状态契约

保留现有连接状态，但增加一个表面层级状态：

```text
ConnectionState: idle → probing → startingDashboard → ready / failed
Surface: chat ↔ management
```

约束：

- `ready + chat` 是默认可用状态。
- `failed` 必须提供重试和设置，不改变用户 Dashboard URL 或 App 偏好。
- 从 `chat` 到 `management` 不得创建第二个 Dashboard 进程。
- 从 `management` 返回 `chat` 不得重建 Agent 会话或修改消息历史。
- 连接重试不能在流式聊天过程中静默刷新 WebView。

## 7. 设计风险

1. Dashboard 是否支持可靠的 `/chat` 深链接，必须用真实构建产物验证，不能只凭路由文件名。
2. 如果“隐藏导航”依赖 Dashboard DOM 或 CSS 类名，会形成脆弱耦合；首选壳层导航和已有
   路由，必要时只做版本化的主题 token 注入。
3. 自动启动的 30 秒探测窗口可能让用户误以为 App 卡死；设计需要显示阶段、取消 / 返回
   管理入口和日志详情，但不把完整日志默认放进聊天主画面。
4. 远程 HTTPS Dashboard 不能由 App 代为启动；聊天优先设计必须继续区分附着和本地 owned
   进程。

## 8. 推荐决策

先实施方案 A，形成一个单迭代、低 footprint 的聊天入口优化。只有当真实验收证明 WebView
   无法满足键盘、焦点、会话恢复或流式交互时，才把原生 Swift 聊天客户端作为新的独立
   设计轮，而不是在本轮逐步混入第二套聊天状态。
